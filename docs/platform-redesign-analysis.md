# LLMmodol 平台重构分析

更新时间：2026-10-01（现状复核）

## 目标与边界

把当前以终端启动和模型调用为主的本地项目整理成一个可操作、可观察、可发布的本地 AI 平台。核心是同一个 Web 工作区管理模型、外部 API、聊天文件、Agent 工作流、运行状态和 Harness；推理继续由 Python 管理，不把模型装载逻辑复制到 Java。平台本身提供 OpenAI 兼容接口；用户也可以录入第三方模型的完整 URL 与 API Key，再从平台选择该远程模型。

## 项目模型盘点

当前本地模型登记表共有 9 个项目：

| 类型 | 可调用模型 | 用途 |
| --- | --- | --- |
| 对话生成（6） | Qwen3.5 0.8B、Qwen3.5 2B、Qwen2.5 1.5B Instruct、Gemma 3 1B IT、Gemma 4 E2B IT、Phi-4 Mini Instruct | 对话和工作流中的 LLM/Agent 节点 |
| 文本转换（1） | FLAN-T5 Base | 文本到文本转换节点 |
| 向量（2） | BGE-M3、Qwen3 Embedding 4B | 文件语义检索；不进入聊天模型选择器 |

另有一个独立的可选 GGUF 运行时：Qwen3.8-27B Q3_K_M。它通过 llama.cpp 运行，和 Transformers 模型共用本机 GPU/系统内存，所以需要由统一运行时锁保证切换前先卸载另一个后端。

以下 8 个模型保持不可调用，并且不应出现在模型选择器、Agent 选择器或 OpenAI `/v1/models` 中：GPT-2-small、GPT-2-medium、MobileLLM-R1-950M、Qwen3-Embedding-0.6B、DeepSeek-Coder-1.3B-Instruct、Xmodel-2.5，以及两个 m-a-p 混合架构实验模型。

远程模型的用户路径是：在“模型与 API”录入显示名称、完整服务 URL、API Key，可发现远程模型并做连接检查；聊天或工作流再选远程模型。平台的 `/v1` 则供用户自己的程序连接本平台。两者都是需要的能力，但角色不同：一个是上游连接器，一个是平台下游 API。

## 当前实现为何达不到预期

1. 聊天与基础文件提取、模型切换、远程 API 配置、平台 OpenAI 兼容端点、工作流草稿/发布、SQLite 运行记录已经存在；这部分应保留和演进，而不是从空白重写。
2. Harness 已迁移到 LangGraph；本轮继续补齐循环语义、并行汇总、可复用 Agent 子流程、结构化输出、有限队列和顶层并发背压。
3. 工作流编辑器已经换成 React Flow，但此前节点种类与执行语义仍不成体系；这一轮增加了 Loop、Parallel 与子 Agent 调用，并把 JSON Schema 输出校验接入执行器。
4. 监控页已有 CPU/内存/GPU、推理吞吐与 Harness 运行指标及告警事件历史；现在增加持久化阈值设置、近期 Run 状态筛选、父子 Agent 标记、失败率告警直达 Trace 和基础脱敏诊断导出。仍需完整进程/节点关联和队列压力控制。
5. Qwen3.8-27B 已实测可启动并返回结果，但性能和资源预算需要明确呈现，不能把“成功启动”说成适合并发服务。
6. 发布闭环之前缺少“从 Studio 试跑不可变已发布版本”的路径；现在增加本机预览端点及发布控制台，避免只能编辑草稿试跑、上线版本却无法在 UI 验证。

## 本轮详细审计：已有功能与产品缺口

### 模型/API 的边界

- 本地选择器中的 9 个登记项分属三类：6 个对话模型、1 个文本转换模型和 2 个嵌入模型。8 个专项/实验模型不应该进入可调用列表。Qwen3.8-27B 是单独管理的 GGUF runtime，不是 Transformers 注册表中的普通模型。
- “添加外部模型”与“别人调用本平台”是两条方向相反的 API 路径。前者是上游 Provider：配置 OpenAI-compatible 服务地址和 Key、发现模型、连接检查，再让聊天或工作流调用。后者是本平台对外提供 `/v1/*`。当前代码已分别具备这两类入口，前者通过 OpenAI SDK，因此不等于支持任何任意厂商协议。
- Provider 密钥通过 Windows Credential Manager 存放，页面读取时只给出是否已设置。单个 OpenAI-compatible Key 可以保护本平台的聊天、嵌入、文件与已发布 Agent API；目前还缺按调用方区分的多 Key、额度/速率限制、Key 使用审计和一致的错误/usage 回执。

### Agent 图与执行语义

- 编辑器及引擎现有 Start、End、Agent、LLM、Tool、Condition、Loop、Parallel、子 Agent、Approval、Transform。草稿保存、发布版本快照、试运行、文件 ID、工具 Schema、JSON Schema、事件 Trace、父子 Run 记录和 checkpoint 恢复都已经接入。
- 之前最直接的正确性缺口是：节点重试耗尽后没有错误出口，异常会结束整个 Run。本轮已补可选错误连线、兜底节点的 `{{error}}` 上下文、错误事件与画布错误边；后续仍需扩展带副作用工具的补偿/幂等语义。
- 本轮还修正了条件路由的数据时序：条件节点执行后会把 `matched` 结果写入自己的变量，路由器现在读取该结果，不会用条件节点自己的输出覆盖原来的 `last_output` 再进行第二次判断。
- 子 Agent 审批曾被拒绝，会限制模块复用。本轮已打通父级审批代理：任意嵌套层的子 Run 等待审批时，父 Run 同步暂停并呈现审批内容；恢复会递归处理实际等待审批的同一个子 Run，再从子工作流节点的 checkpoint 继续。
- 并行能力现在分两层：Parallel 适合一个节点内运行 2–8 个模型/工具任务；图级 Fan-out/Fan-in 则让 2–8 条独立画布路径执行完整节点链，包含条件、循环、节点重试、错误出口，再由 barrier 等待所有分支并合并结果。图级路径使用 LangGraph `Send` 与 SQLite checkpoint；仍不允许在分支内嵌套图级 Fan-out/Fan-in、人工审批或可暂停子工作流，校验器会在保存/发布前指出这些连接。
- 条件和循环已经能跑，但数据端口还是节点变量与模板字符串，缺字段级映射、变量作用域、显式分支合流策略、数据类型检查和发布前死路/无效循环提示。流程图因此能表达执行顺序，尚不能完整表达复杂 Agent 数据流。
- 已有 `/v1/agents` 列表、发布快照运行和异步状态查询；目前仍是开发者 API，不是面向终端使用者的完整 Agent 部署页。缺 Agent 在线试聊/分享入口、会话式多轮 ID、Agent SSE 流式输出、易复制的请求示例、版本回滚/对比与调用统计入口。平台 API Key 目前也未细分到 Agent、用户或调用方。
- 运行记录已存节点及工具事件；下一步应验证事件是否一致覆盖每次模型尝试、错误、超时、取消、审批、恢复、子 Run 和并行分支，并在 UI 中提供可筛选、能回到画布节点、显示输入/输出摘要及重试因果的 Trace，而不只显示事件列表。

### Harness 与监控

- 当前 Harness 是“LangGraph 图执行 + SQLite checkpoint + 项目自己的运行/队列/事件数据库”，不是完整套件的 LangGraph 产品。LangGraph 解决图路由与状态持久化，不会自动提供部署 UI、隔离、运行配额、模型资源仲裁或操作员诊断。
- 队列上限、Run 状态和恢复基础已存在，但活动槽由单进程控制，SQLite 队列面向本机单服务实例；它不是多进程租约队列。服务重启后未开始项可以重入队，已运行中的工作流需要 checkpoint 恢复。这个边界应该在状态 UI 中解释清楚。
- 监控目前有 5 秒系统采样、历史曲线、Harness 24 小时聚合、告警历史/确认/恢复、模型调用/token/延迟汇总和部分 GPU runtime 数据；本轮增加顶层实时 Run 列表、可筛选的近期 Run/子 Agent 执行台账，并可从失败率告警跳转至最近失败 Trace。运行台账已针对中等屏幕改为全宽表格，窄屏改为卡片布局；实时列表显示节点、等待时间和子 Run 数，近期台账不返回工作流输入或文件内容。现有脱敏诊断包可下载资源与失败元数据；仍需告警规则滞回、Run→节点→模型/工具统一 trace ID、TTFT/生成速率分布、队列等待与资源压力关联、采样/事件保留策略和数据库/checkpoint 清理。
- 当前监控要从“显示数字”升级为“回答为什么”：失败 Run 应能从告警或统计项进入事件树；节点耗时应与模型提供方、输入/输出 Token、重试和错误关联；模型装载/运行状态应与 CPU、系统内存、VRAM、请求队列同屏显示；每项指标需区分未采集、无硬件支持、真正的 0 和过期数据。
- 不能为了“监控完整”无条件叠加一套重型外部服务。优先把事件与指标做成有明确 schema 的本地遥测，接入 OpenTelemetry 的 trace/metric/log 语义；需要独立可视化或远程导出时再加可选 exporter。这样保留本机离线可用，同时可借用成熟生态。

### 界面与交互

- 已有暖纸白、松针绿、陶土色的主题，但主题色不能单独建立产品辨识度。工作流 Studio 常用字号提高到约 9–14px、节点放大到 250×166；本轮增加画布优先布局，步骤库/属性检查器可独立开关，窄视口默认释放画布空间，点选或新增节点会自动打开检查器；运行 Trace 可折叠。
- Trace 事件现可在流程版本一致且草稿干净时定位并居中对应画布节点，检查器随之打开；若草稿已经变化，面板明确说明版本不一致并停用跳转，避免把旧运行映射到不同定义。整体布局仍需进一步做可调整宽度、画布/Trace 底部 dock、节点组和更强的状态可视化。聊天、模型管理和监控应该各有内容布局，不把所有页面套成同一种卡片网格。
- 字体尺寸、空状态、加载/故障/过期状态、窄屏布局、键盘操作、焦点和对比度都属于设计验收标准。仅换图标、换主色或追加阴影不构成一次有效改版。

### 实时运行复核（2026-10-01 21:48）

- 本机 `/api/models` 返回的 9 个登记模型文件都可用；专项目录模型仍由排除列表隔离。Qwen3.8-27B GGUF 文件已完整安装（13,404,051,168 字节），但检查时运行状态为 stopped；没有正在执行的模型请求。机器采样显示 32 GiB 系统内存、RTX 5060 Laptop GPU 约 8 GiB 显存，当前 GPU 显存使用约 1.4 GiB。
- 当前数据库中有 2 个草稿工作流、均未发布。Harness 最近 24 小时记录 7 个终态 Run：6 成功、1 失败；顶层活动数和队列数均为 0。失败发生在文件研究员 Agent 节点，两次尝试都只留下异常文本 `KeyError: 'Name'`，随后 Run 失败。当前事件没有异常堆栈、模型/provider 关联或统一 trace/span 标识，单从 Trace 无法解释此错误来源。
- 同一时点监控只显示“运行状态正常”。失败率为 1/7（14.3%），低于当前 20% 告警阈值，因此没有失败率告警；这符合数值阈值的实现，却不适合作为整页状态文案。监控应把“系统资源健康”和“最近存在失败 Run”分开呈现，并始终保留可点击的最近失败入口。
- 复核同时说明了下一步的顺序：先补足异常与模型调用的关联并定位 `KeyError: 'Name'`，再让输入/输出 schema、变量映射、运行 Trace 和发布 API 使用同一份版本化工作流契约。否则继续增加节点类型会扩大配置面，却仍无法可靠地传数和定位故障。

## 改造优先级与验收标准

1. **执行正确性**：已做 retry/error routing 与 `{{error}}` 上下文、子 Agent 审批恢复、图级并行/汇合及分支审批/子流程恢复；后续继续检查外部副作用的幂等边界和嵌套并行。每个能力都要同时有画布配置、后端校验、checkpoint 行为、可读 Trace 和失败路径。
2. **Harness 可观测性**：为一次 API/聊天/Agent Run 建立统一关联链，向下贯穿子 Run、节点尝试、模型调用与工具调用；增加队列/运行/审批/错误/延迟/Token/TTFT 维度，提供可配置告警、去敏诊断导出和本地存储保留策略。
3. **工作流易用性**：流程定义采用显式输入输出和分支/合并协议，表单由节点 Schema 驱动；画布要表达错误分支、循环边、并行组、子 Agent 版本与节点状态。发布时显示结构校验、不可达节点、缺参数和能力差异。
4. **视觉重做**：从布局、字体、间距、分层、图节点信息密度和状态语言重做；用实际屏幕尺寸检查而不是只在 CSS 中完成。工作流 Studio 与聊天、运维页使用一套品牌，但保留各自任务特征。
5. **部署/外部接口**：保留上游 URL+Key Provider 与平台下游 API 两种能力，统一鉴权/模型 ID/错误/usage；补多 Key、限额和审计前，明确目前单机单用户 API 的部署范围。
6. **Qwen3.8-27B**：维持按需启动、单并发和 4K 上下文；记录自动 CPU/GPU fit 实际落点、模型 RSS/VRAM、加载时间和生成速度。自动 fit 会尽可能把能放下的部分放进显存，不足部分仍走系统内存；只有自动装载无法就绪时才会启动 CPU-only 回退，因此回退可用不等于速度可接受。图片理解还需要正确的多模态 projector/处理链，现有纯 GGUF 文件没有接通。

**明确的验收证据**：重试耗尽后走错误出口、无错误出口时 Run 如实失败；在审批处暂停、跨重启恢复且不重复执行已完成的副作用；并行分支能显示部分失败与合并结果；从监控告警可打开对应 Trace；阈值修改真实影响告警；平台 UI 可读、状态不混淆；Qwen 的混合落点、CPU 回退和长输出吞吐都展示实测结果，而不是只标注“支持”。

## 本轮实际落地与能力边界

### 已落地

- Agent 工作流入口已切换到单独的 React/React Flow Studio。工作流 Studio 与主工作区统一采用纸白底、松针绿导航和陶土色动作强调；聊天、模型/API、运行记录、监控都已接入同一套主界面主题。工作流页提供步骤库、画布连线、检查器、流程校验、文件输入、试运行 trace、审批按钮、保存草稿、发布/停止发布及 Agent API 地址。
- 发布弹窗已升级为发布控制台：试运行和 API 接入分栏；本机预览端点通过已发布定义和版本号直接创建 Run，不读草稿。可以上传文件、轮询节点 trace、看最终输出、审批或取消；公开 API 示例包含 URL、curl、文件上传及 Run 查询路径，仍通过 Bearer Key 调用。
- 实际服务验收发布版“快速计算链”v1，以 `40 + 2` 运行安全计算器，结果为 `42`，UI 收到排队、节点、工具调用与完成事件；随后停止发布并恢复该工作流草稿状态。构建、Python 编译通过，重启服务前运行数为 0。
- Agent 编辑区由固定三栏改为可折叠两侧抽屉：视口不宽时默认显示画布，侧栏由画布工具栏开关；点选/新增节点会自动打开设置。底部试运行面板可收起，Run 状态和版本仍留在标题行。Trace 的“定位节点”会平移画布、选中节点并打开检查器；只有运行快照和当前干净草稿版本相同时才允许跳转。浏览器真实 Run 验证 `40 + 2 → 42`、Trace 定位和版本不一致保护均符合预期，浏览器控制台无错误；验证未保存的描述编辑通过刷新回滚。
- 原来的自写顺序循环已替换成 LangGraph `StateGraph` 执行路径。Harness 仍负责版本快照、数据库运行记录、节点/工具事件、重试、超时、取消、文件状态及平台 API；LangGraph SQLite checkpointer 负责状态持久化。主流程审批使用静态 interrupt breakpoint，图内分支审批使用带中断 ID 的持久化 interrupt；并行待审项逐个显示和定向恢复。
- 已通过平台 HTTP API 实际跑通一个临时验收流程：输入 → 整理 → 等待审批 → 批准并恢复 → 输出。验收 workflow、run 和 orphan checkpoint 已清理；数据库中保留的两个流程是原有“快速计算链”和“文件研究员”。
- 监控接口现可聚合 24 小时运行成功率、中位数/P95、排队时长、失败次数、节点重试、工具失败、审批和恢复数、慢节点、工作流成功率、最近错误以及 checkpoint 文件占用；资源阈值会在监控页汇成状态卡，并能从失败项跳到完整 Harness trace。
- 构建器能输出可部署页面到 FastAPI 静态路由；本机 `/studio` 已在真实服务进程验证返回 200。启动器的 build ID 改为进程加载时固定，避免旧服务在源码变更后误报成新版本。
- 增加 Loop 节点：比较用户输入、上一步或节点变量，支持最多 50 轮，节点访问计数通过 LangGraph reducer 合并，仍受每次运行 100 步总上限保护。
- 增加图级 Fan-out/Fan-in：2–8 条画布路径由 LangGraph `Send` 真正并发启动；每条路径隔离自己的变量、last output、错误与访问计数，支持模型/Agent/工具/文本整理/条件/循环/原有 Parallel，分支错误出口可单独恢复，汇合点按分支 ID 保留状态、输出、变量和错误。
- Fan-in 是 barrier：每条路径必须到达唯一配对汇合节点，主流程只会在所有路径报告完成/失败后继续；失败策略可选“失败即停止”或“保留失败结果继续”。校验器拒绝跨分支共用节点、从主流程绕入分支、错误配对和嵌套图级 Fan-out；审批与可暂停子工作流可在分支中挂起并在同一 checkpoint 恢复。
- Fan-out 并发数可设 1–8，分支节点各有最多 100 步预算；整个运行通过 reducer 计量并预留最多 2,000 个执行动作，避免条件循环或重复分流无限耗用资源。正在执行的分支任务由 LangGraph checkpoint 保存；重启后恢复测试确认会继续未完成分支并保留已完成分支结果。
- Studio 增加图级“并行分流”节点，添加时同步建立配对“并行汇合”；每条分支有独立画布端口、路径入口、名称和并发上限。汇合节点可配置分支失败策略，事件轨迹显示分支启动、节点执行、失败、汇合和最终输出。
- 图级并发通过真实引擎验证：隔离 SQLite checkpoint 运行含条件、错误出口和 Fan-in 的两分支流程；“失败即停止/保留失败并继续”均按配置执行。中途取消后关闭并重新打开 checkpointer，已完成分支不重跑，未完成分支从节点 checkpoint 恢复；运行服务重启后 `/api/workflows/validate` 也已确认接受该图定义。
- 增加 Parallel 汇总节点：2–8 个 Agent/LLM/工具/文本整理分支可限并发执行，按分支 ID 聚合输出并保存逐分支开始/完成/失败 trace；结构校验会检查分支 ID、工具、参数和并发上限。
- 并行节点检查器已改为分支卡片编辑器：新增/移除分支、分支 ID/名称、Agent/模型/工具/文本整理类型、模型提示词、工具权限、工具参数、输出 Schema、最大输出 Token、随机度、重试和超时都可在 UI 内配置，不需要直接维护整个 branches JSON 数组；分支配置会经后端验证并由执行器实际应用。
- 普通工具节点和并行工具分支会按注册工具的参数 Schema 自动生成输入控件；枚举使用下拉框、必填项有标记、headers/body 等对象参数使用局部 JSON 编辑器。
- 增加“调用 Agent”子工作流节点：选择已发布 Agent 时把其发布定义与版本快照写入父工作流，执行产生有父运行/父节点关联的持久化子 Run，支持输入模板、文件继承、取消传播、循环引用和最大 5 层检查。子 Run 的审批会向上传递到父 Run；拒绝后再次进入审批也会重新中断，不触发审批节点失败或重复运行已完成节点。
- 增加 Harness 顶层运行调度：最多 2 个顶层运行同时执行，最多持久等待 100 个顶层运行；超限时 UI/API 得到明确的 429。待执行项留在 SQLite，服务重启后重新入队；已执行中的运行标记为中断，由用户从 checkpoint 恢复。子 Agent 不占顶层并发槽，防止父流程持槽等待子流程造成死锁；父运行恢复时按节点访问轮次复用或恢复对应子 Run，避免重复执行已完成的子流程。
- 增加可选节点错误出口：Agent、模型、工具、文本整理、条件、循环、并行与子 Agent 节点在重试耗尽后可走独立错误边；`{{error}}`/`{{last_error}}` 提供失败节点、异常类型、消息和尝试次数；无错误出口仍保持原有失败语义。画布边、属性检查器、结构验证、可达性检查、运行 Trace 与主界面历史详情均可识别错误路由。
- 修正条件节点分支判定：执行阶段的 `matched` 结果作为唯一的该次路由依据，解决 `last_output` 被条件节点返回值覆盖后又重复比较的问题。
- 修复审批拒绝后回到同一审批节点的断点：恢复执行仍在所有审批节点前设置断点，允许“退回修改 → 再次审批”循环正常暂停。
- 补齐并行分支实际重试与超时：每个分支按自身设置独立重试和限时，失败事件记录分支 ID、尝试次数和原因；总分支失败后才返回 Parallel 节点的错误处理。
- 审批暂停中的顶层运行现在可以直接取消；Harness 会递归结束其等待审批的子 Run 并清除 pending，避免流程永久停在等待状态。子 Run 由父 Run 统一控制，API 和 Studio 都阻止单独取消一个仍被父流程等待的子 Run。
- LLM 与 Agent 节点可选 JSON Schema；执行器会要求 JSON-only 输出、解析 fenced JSON 并用 Draft 2020-12 校验，失败进入该节点已有的重试和 trace 路径。Schema 限制为 16 KB，且只接受本地 `$ref`。
- Harness 告警事件以稳定指纹记录首次/最近发生、采样观察次数、当前/确认/恢复状态；出现次数由 5 秒采样器更新，读取监控页不改变计数。CPU、内存、显存阈值要求连续 3 个资源样本，GPU 温度和 Harness 失败率按即时/24 小时统计。
- Harness 每次 LLM/Agent 模型请求现在记录模型/provider、请求耗时、成功/失败和 token 用量；远程 provider 采用接口 usage，本地 Transformers 通过当前模型 tokenizer 统计格式化输入和生成文本。监控汇总 24 小时调用、错误、输入/输出 token 和逐模型平均耗时；此前已完成的运行没有追溯数据。
- 运行监控新增顶层实时运行列表，覆盖排队、执行中、取消中、待审批和待恢复状态；列表避免将父流程代理等待的子 Run重复列作另一条工作，并支持从流程节点、耗时和子 Run 数直接进入完整 Trace。
- 监控告警阈值已可在“运行健康”面板展开编辑并保存到 SQLite；CPU、内存、显存、GPU 温度、采样超时、队列等待/容量和 Harness 失败率阈值由采集器实际读取。资源连续采样数可设 1–12 次；内存/显存和失败率严重阈值必须高于关注阈值；恢复默认、范围校验和下次采样生效均已接入。
- 子 Agent 审批已在隔离临时数据库中做三层端到端检查：叶 Agent 首次等待、退回修改后再次等待、从根 Run 批准后三级父子 Run 全部完成；叶审批 Run ID 保持不变，已完成的准备节点只执行一次，父节点在审批前没有提前继续。审批挂起事件与实际审批事件分开记录，避免把代理等待重复计入审批请求数。
- Parallel 分支在临时工作流中验证了单分支瞬时故障后按配置重试并汇总成功，以及超时后产生可读的失败原因；结构校验也拒绝超范围重试和超时设置。
- 三层暂停审批树的取消行为已在临时 SQLite 中验证：直接取消子 Run 会被拒绝，取消顶层 Run 会递归结束三级 Run 并清空所有审批 pending。
- Loop、Parallel 汇总、子 Agent、JSON Schema 和 trace 已在独立临时 checkpoint/数据库执行冒烟检查；父流程和子 Run 成功完成并保留版本、父子关系。工作流 API 校验端确认 Loop/Parallel/子 Agent 结构合法。监控读接口返回持久化告警历史与未确认数量。
- Fan-out 分支审批已补入图执行内核：中断 ID 与 LangGraph task 对齐，多个并行审批逐个展示并只恢复被选择的分支；审批决定写入该分支局部变量和 trace。子 Agent 在 Fan-out 分支内等待审批时会挂起分支、递归恢复子 Run，再从原子工作流节点继续。临时 SQLite/Harness 验收通过“子 Agent 审批 → 另一分支审批 → Fan-in 完成”；平台 HTTP API 验收通过两条独立审批，服务重启后继续同一 checkpoint 并完成汇合。测试用工作流、Run 与 checkpoint 均已清理。

## 建议的目标架构

### 1. 本地 Web 工作台与 Python 服务

继续用 FastAPI 服务前后端同源页面。前端从手工拼接复杂画布迁到 React/React Flow：React Flow 有拖动、缩放、多选、自定义节点、分支 Handle、控制器等成熟交互，工作流草稿继续使用平台现有 JSON/API 保存。可保留现有聊天和模型管理 API，逐页替换 UI，避免一次性切断可用功能。

视觉方向改成暖纸白工作台、墨色正文、深青导航与赭红/琥珀点缀，画布采用纸纹网格和清晰连线；减少常见的紫色霓虹、卡片堆叠和泛化 AI 渐变。Agent 画布用左侧步骤库、中间大画布、右侧属性检查器、底部运行时间线的稳定布局；对话界面则保持留白和内容为主。

### 2. 统一模型路由与外部 API 连接器

模型连接统一分成本地 Transformers、llama.cpp GGUF、远程 OpenAI 兼容服务三类。调用侧传入模型 ID，路由层负责 provider、鉴权、流式输出、错误归一化和 usage 统计。远程服务保存 URL 与 Key 时不回显明文；连接失败区分 URL、鉴权、模型权限、额度、超时。

平台向外暴露 `/v1/models`、`/v1/chat/completions`、Agent 发布/运行接口和文件上传接口，并有 OpenAPI 文档、Bearer Key 管理及统一错误结构。部署为仅本机时保持 loopback；需要局域网或外网时再配置绑定、认证和 TLS。

### 3. Agent 工作流与 Harness

继续用开源 LangGraph 作为图执行内核，用 React Flow 作为可视化编辑器。平台保留自己的 Harness 管理层，负责工作流版本、发布快照、节点配置 UI、工具注册、运行配额、密钥遮盖、审批、运行记录与平台 API。LangGraph 提供持久化 checkpoint 与中断/恢复等长任务基础能力；React Flow 提供自定义节点和图交互，二者职责清晰。

工作流能力已包含输入/输出、LLM、Agent、工具调用、文件检索、条件分支、循环、节点内并行、图级 Fan-out/Fan-in、HTTP/API、父级人工审批、JSON Schema 输出和已发布子流程；子流程审批（包含图内并行分支中的可暂停子流程）会沿父运行传播，并保留叶级 Run 信息。仍需提供计划触发、try/catch/finally、嵌套图级 Fan-out 和节点级 token/费用统计；基础运行级脱敏诊断导出已接入。HTTP 工具仍需限制目标主机和请求大小；每个节点保留输入摘要、输出、耗时、重试次数、模型/provider、token 用量和错误。当前本地队列适合单服务实例，不承担多进程/多机器的分布式调度。

开源复用判断：本项目已经直接集成 LangGraph Python（MIT，StateGraph、持久化 checkpoint）和 React Flow（MIT，自定义节点、连接端口、画布控制）。Coze Studio（Apache-2.0）与用户要的“类似扣子”最接近，可作为 Agent 创建、调试、发布、API/SDK 和资源组织的产品基准；它自身需要 Docker Compose、模型服务配置和独立账号/模型管理，直接并入会再形成一套服务、凭据和数据模型。Langflow（MIT）提供 Python 组件画布、Flow API 与 MCP 部署，Flowise（Apache-2.0）提供 React UI、Node 服务与 Agent API；它们适合借鉴节点交互或单独验证，但作为第二套完整运行时会重复模型注册、密钥、版本和运行记录。优先继续以本项目的 FastAPI/SQLite 作为控制面、LangGraph 作为执行内核、React Flow 作为编辑器；吸收 Coze 的发布体验和 Langflow/Flowise 的组件/调试设计，逐步补流程导入导出或兼容格式，不同时维护两套 Harness。LangGraph checkpoint 与 stores 是不同层：本项目目前只有按 run/thread 保存的 checkpoint，还没有跨 Agent 的长期共享 memory store。

### 4. Harness 监控与运行诊断

监控至少分三层：

- **整机资源**：CPU、RAM、GPU 利用率、显存、温度、磁盘空间、采样间隔和历史窗口。
- **推理服务**：当前模型/backend、模型进程 RSS/CPU、加载时间、prompt 与生成速度、请求处理中/排队数、错误和超时。
- **Harness 运行**：活动/排队/待审批数量、成功率、延迟分位数、每节点耗时、重试和失败、模型/token 用量、工具调用轨迹、取消与恢复。

阈值与事件历史已覆盖 CPU/RAM/VRAM、GPU 温度、采样延迟、Harness 队列和失败率，并允许阈值配置、确认与自动恢复；面板现区分顶层并发、队列容量和父子 Agent 总运行数。现已提供可下载的基础脱敏诊断包；下一步加告警通知策略、模型未就绪/运行心跳监测和阈值触发趋势视图。采样和健康查询继续放在线程池或异步客户端，不阻塞 API 响应。

## Qwen3.8-27B 本地部署结论

这台机器在本轮实测中识别为 32 GiB 系统内存和 RTX 5060 Laptop 8 GiB 显存。当前下载的 Q3_K_M GGUF 文件约 13.4 GB；使用 llama.cpp `--fit on`、单并发、4,096 context 启动后，权重自动分布到 GPU 与 RAM，实测 llama.cpp 约占 6.9 GiB 显存和 13–13.2 GiB 进程 RSS。一次冷启动约 45 秒；样例请求输入 57 tokens 约 43.46 秒，生成 28 tokens 约 10.31 秒，即该样例生成约 2.62 tokens/s。之后服务重启后的短暖请求测得约 6.3 tokens/s；短答样本不代表长输出稳定速度。结果证明“可以本地跑并由 CPU/GPU 共同承担”，但这是低吞吐、单并发的体验配置；推理时系统可用内存曾降到约 4.6 GiB，不能与其他大模型并行驻留。官方仓库将 Qwen3.8-27B 标为 27B、带视觉编码器的图文模型，原生上下文为 262,144 tokens，并列出的 BF16 仓库体积约 55.6 GB；当前机器运行的是 13.4 GB 社区 Q3_K_M GGUF 和 4K 上下文。模型目录目前只有主 GGUF，没有单独视觉 projector，因此现状是文本推理，不应宣传成已支持图片/视频的完整模型能力。

### 可行性分层

| 使用方式 | 结论 | 落地约束 |
| --- | --- | --- |
| 本地手动短问答 | 可行 | 保持当前 Q3_K_M、4K context、单槽；冷启动有等待，热态短请求实测数 tokens/s。 |
| Agent 工作流调用 | 有条件可行 | 工具/路由优先由 Harness 决定，Qwen 用于少量规划/总结；限制每个 Run 的模型调用轮数与总 token，显示模型排队和端到端耗时。不要让图内 fan-out 同时打满这个单槽模型。 |
| 普通多人并发服务 | 当前不可行 | CPU/RAM 与 8 GiB VRAM 已接近资源边界，低吞吐与内存余量会造成请求堆积。扩展前需更高显存/内存，或独立推理机/远程 provider。 |
| 官方完整精度 BF16 | 当前不可行 | 官方 HF 仓库约 55.6 GB，尚不含运行时、上下文和视觉张量；超过本机 32 GiB RAM，无法按现在方式装入。 |
| 本机视觉输入 | 尚未可行 | 官方模型卡标注具备图像/视频能力，但当前 GGUF 文件夹没有 projector，现有本地 HTTP 路径也只验收了文本。需要单独确认完整多模态 GGUF/processor 组合。 |
| 纯 CPU 回退 | 理论上可装载，性能未证实 | 自动 fit 失败后启动器会重新以 `--n-gpu-layers 0` 启动；CPU-only 的 token/s 与长时间稳定性尚无数据，状态应显式标为“降级”，不能当成功能等价回退。 |

模型卡称 Qwen3.8-27B 为 27B dense，并提供 Transformers、vLLM 与 SGLang 的用法；模型卡的 Transformers 方式依赖 `AutoProcessor` 与 `AutoModelForMultimodalLM`，官方还将量化模型导向 llama.cpp/LM Studio/Ollama 生态。此项目目前的混合 CPU/GPU 测量来自本地 llama.cpp Q3_K_M，不是完整 Transformers BF16 部署；自动 `--fit` 会设置未显式指定的内存相关参数，并可调整层卸载与 context，但不会在运行时动态搬层来消除算力瓶颈。CPU/GPU 共担解决“装得下”，不等于获得 GPU-only 速度或多并发能力。

实际建议：Q3_K_M + 4K context + 单槽作为“本机可选模型”；当前启动参数使用 16 个 CPU 线程、`--n-gpu-layers auto`、`--fit on`、1 GiB 设备余量和 CPU 回退。llama.cpp 自动 fit 优先把可容纳的部分放到 GPU，其余权重留在系统内存；开模型前卸载 Transformers 模型，关模型后释放 provider 和运行时占用。启动失败需把最后日志、已用显存和 RAM 一并展示，再进入可见的 CPU 回退状态。当前 CPU-only 性能没有单独测试，因此不对它的速度作承诺。还需做长对话、长时间、多轮重复调用和低内存稳定性测量；暂不作为默认模型。

llama.cpp 文档确认 `--fit` 会调整尚未显式指定的参数以适配设备内存，`--fit-target` 控制设备余量，`--fit-ctx` 限制自动调整后的最小 context；所以自动 CPU/GPU 分担应由 llama.cpp runtime 控制，而不是在前端随意估算 GPU 层数。

## 实施顺序与验收

1. **稳定性底座**：运行时互斥与回滚；监控查询移出事件循环；模型/进程的真实占用与 GGUF 吞吐入库；确认启动、停止、切换模型状态正确。
2. **Harness 内核**：加入 LangGraph 和持久化 checkpoint；保留现有数据库/API，通过适配层迁移旧工作流，先实现审批/恢复、事件 trace 与兼容旧发布快照。
3. **Agent 能力**：扩展节点协议、工具权限和父子运行记录；有限持久队列、父子运行恢复、嵌套审批传播与可视化并行分支编辑已加入。后续补齐图级任意并行/汇合语义。
4. **工作流界面**：继续完善自动布局、缩放/平移、多选、节点搜索/分组、结构化输入表单、运行详情和草稿/发布版本差异。
5. **Harness 运维面板**：已经有资源曲线、模型吞吐、Run/node trace、失败聚合、告警历史、可配置阈值和基础脱敏诊断导出；下一步增加告警策略与受控队列/任务重试。
6. **端到端验收**：检查指定模型可见性、远程 URL+Key provider、聊天文件上传、至少一个 Agent 运行/工具/审批/恢复/发布/API 调用、GGUF 启停与内存回退、监控曲线和界面响应时间。

基础稳定性、LangGraph checkpoint、React Flow 画布与 Harness 监控已落地；Loop、节点内 Parallel 与图级 Fan-out/Fan-in、可视化分支/汇合、已发布子 Agent、嵌套审批和跨分支暂停恢复、JSON Schema、有限持久队列、可配置告警历史、节点错误出口和基础脱敏诊断导出已接入。嵌套图级 Fan-out、Harness 运维界面信息层级和视觉辨识度仍待完善。Qwen3.8-27B 可以在当前设备 CPU/GPU 混合运行，但建议只作为单并发、低吞吐、按需加载模型；长时稳定性与 CPU-only 回退吞吐仍待测量。

- 后端异常事件增加受限诊断字段：异常类型、触发模块/函数/行号、有限调用帧与异常原因类型；不采集局部变量、源码行或绝对路径。工作流节点、图内并行分支、模型/工具调用和 Run 结束错误均写入该字段。
